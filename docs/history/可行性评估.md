# 小米早期蓝牙语音遥控器接入 SayAll（remote-mic-app-windows）可行性评估

> **方向转向（2026-11-14 晚）**：经评估，该老款遥控器无 ATVV 服务、语音走私有透传且连接即断，改造不划算。已决定**彻底抛弃遥控器**，改为开发 **Android 手机 App 直接当遥控器 + 手机麦推流到电脑**，电脑端用独立轻量 Python 服务接收。新主线设计见 `手机遥控麦方案.md`；本文档保留为遥控器侧调研与取证存档。

评估日期：2026-11-14
评估对象：本机已配对的小米蓝牙语音遥控器（VID_012717 / PID_32B8 / REV_4981，地址尾号 D4B8FF93F635）
参考仓库：https://github.com/GetSayAll/remote-mic-app-windows （main，已浅克隆到本目录 `remote-mic-app-windows/`）

> 证据分级：【实测】本机探针/注册表读到；【代码】仓库源码核实；【推断】基于同类设备与协议常识，需真机复核。

## 一、结论先行

| 接入层面 | 可行性 | 说明 |
| --- | --- | --- |
| 官方安装包开箱即用 | **不可行** | 官方只适配 RC001（遥控器 2）/ RC003（2 Pro）；本机被识别为 `Unknown` 型号。 |
| 只改名称 / 型号白名单就让语音工作 | **不可行** | 代码语音链路虽不按型号做门禁，但强依赖一组固定的 ATVV GATT 服务；本机 GATT 列表中未见该服务，连接会在服务发现阶段失败。 |
| 基础按键映射（方向 / 确定 / 主页 / 菜单等 HID 键盘键） | **部分可行，待复核** | 按键走标准 BLE HID 键盘通道，Windows 原生挂载；这部分与语音协议无关，理论上可被 Raw Input / SendInput 捕获。返回、音量± 在官方 RC003 上都收不到、需提权 Helper，老款通道归属未取证。 |
| 语音（按住说话 → 转文字） | **属协议级二次开发，成本高** | 本机语音数据走的是 Realtek 私有串口透传服务（非官方适配的 ATVV 标准服务），帧格式 / 编码无公开文档，需要先抓包逆向，再在仓库中新增一条私有协议解码链路。 |

**一句话判断**：这台机器不是官方支持的 RC001/RC003，且语音通道协议大概率与 SayAll 适配的 ATVV 不同；"改个白名单"解决不了语音，要用上语音功能需要自行逆向私有 BLE 协议。若目标只是"拿一支便宜遥控器当电脑无线麦"，直接买二手 RC001/RC003 的成本和风险都远低于改造这台老款。

## 二、SayAll 项目是怎么工作的（代码事实）

技术栈：Tauri 2 + Rust（`crates/sayall-core`、`crates/sayall-windows`）+ Vue 3。

### 2.1 语音链路（四层）

1. **BLE GATT 取流**：通过 WinRT BLE 连接遥控器，订阅 ATVV 服务的音频 / 控制通知特征。
2. **协议解析 + 解码**：ATVV 会话握手（能力协商 → 麦克风打开 → 推流 → 续约 → 关闭），上行音频帧解 IMA ADPCM 为 PCM（16 kHz / 8 kHz，由能力字选择）。
3. **虚拟声卡输出**：WASAPI 把 PCM 写入 VB-CABLE 虚拟声卡的 CABLE Input。
4. **第三方语音输入法拾音**：豆包输入法 / 微信输入法 / Vokie 等从 CABLE Output 采集，完成转文字并落到输入框。

### 2.2 协议常量（`crates/sayall-core/src/atvv.rs`、`crates/sayall-windows/src/ble.rs`）

| 项 | UUID / 值 |
| --- | --- |
| ATVV Service | `AB5E0001-5A21-4F05-BC7D-AF01F617B664` |
| Transmit（写） | `AB5E0002-…-B664` |
| Audio（notify） | `AB5E0003-…-B664` |
| Control（notify） | `AB5E0004-…-B664` |
| 控制命令 | `0x0C` 开麦 / `0x0D` 关麦 / `0x0E` 续约；能力 `0x0B`；流开始 `0x04`；解码器同步 `0x0A` |
| 编码 | IMA ADPCM，高/低 nibble 序可配；16 kHz（codec 0x02）或 8 kHz（0x01） |

### 2.3 型号识别（`crates/sayall-windows/src/lib.rs`）

- 扫描阶段按**广播名**过滤（`is_supported_remote_name`），白名单含：`MI RC`、`Xiaomi Bluetooth Remote 2 / 2 Pro`、`小米蓝牙语音遥控器`、`小米蓝牙遥控器2 / 2 pro`、`ARN9`。
- 型号细分（`remote_model_from_name` / `remote_model_from_model_number`）只认 `RC001`、`RC003`、名称含 `ARN9`；其余一律 `RemoteModel::Unknown`。
- **型号枚举只用于界面显示**：服务发现、ATVV 会话、ADPCM 解码都不按 `Rc001/Rc003/Unknown` 分支；真正的硬门禁是"能不能找到 ATVV 服务与特征"，找不到则报 `VoiceServiceMissing`。

### 2.4 按键链路

- 普通键：Raw Input 按设备归属 + `SendInput` 注入快捷键 / 打开应用。
- RC003 的返回 / 音量± 在 Raw Input 两条通道都收不到；官方方案是独立提权 Helper + Frida Gadget 注入承载设备的 `WUDFHost.exe`，在报告层改写 / 清空这几个 usage（`hardware/RC003/`、`rc003_bridge.rs`）。这是可选增强轨，Helper 不在场时基础语音与基础按键不受影响。

### 3.3 与官方 RC003 真机取证对照

仓库 `hardware/RC003/evidence/gatt-probe-enum.log` 中 RC003（REV_00A4）连上后枚举到 **9 个服务**，关键项：

- `AB5E0001-…-B664` **ATVV**：0002 write / 0003 audio notify / 0004 control notify；
- `8A7A0001-2C42-C2A2-…` 小米私有服务（5 特征）；
- `000001BF-…`、`0000FE59-…`（各含私有特征）；
- 2A24 型号串读出为 `RC003`，2A29 厂商 `MIO M`。

**本机对照差异**：

- 本机**未出现** `AB5E0001` ATVV 服务，也没有 `8A7A0001` / `01BF` / `FE59`；
- 本机私有服务基址 `3C17-D293-8E48-14FE2E4DA212` 是 **Realtek RTL8762x BLE Data Transfer Service（串口透传）** 的默认厂商基址（FFE0/FFE1 一族），与 RC003 的私有服务基址完全不同；
- PID 同为 `32B8` 但 REV 不同（本机 `4981` vs 取证 `00A4`），服务集也不同——**同 PID 不代表同固件 / 同协议**。

### 3.4 未闭环的取证项

- **ATVV 服务缺失（已闭环）**：3.2 的连接态全量服务树已确认本机无 `AB5E0001`，"服务仅在连接后才暴露"的小概率排除。
- **2A24 型号串 / 2A29 厂商串仍未读出值**：nRF Connect 截图只列出特征属性，未点 Read；本机 PowerShell 5.1 对 WinRT `IBuffer` 投影受限也未能取值。官方型号代号（可能是某 XMRM 型号）待在 nRF Connect 里点 2A24、2A29 的读取箭头补一张值截图。
- **语音帧通道与编码未抓包**：本次为静态服务列表，未订阅任何 Notify、未在按住语音键时记录上行帧。语音数据究竟从 `D1FF/A001` 还是 `6287/6487`（或某条 2A4D HID Report）上行、编码是否 IMA ADPCM、采样率与帧头格式，均需订阅通知后按键抓包确认（见第五节步骤 1、3）。

### 3.5 连接即断现象与本机日志证据

**现象**：手机 nRF Connect 与电脑表现一致——连上、读到服务信息后很快断开；nRF Connect 顶部状态为 `NOT BONDED`（未绑定）。

**本机 BTHUSB 事件日志（System 日志，只读取证）**：

| 时间 | 事件 | 内容 |
| --- | --- | --- |
| 21:18:39 | 8 | 远程适配器 `d4:b8:ff:93:f6:35` 成功与本地适配器配对 |
| 22:25:06 | 10 | 链接密钥被删除，不再是成对设备 |
| 22:25:24 | 8 | 再次成功配对 |
| 22:31:04 | 10 | 链接密钥再次被删除，不再是成对设备 |
| 08:12:03 | 18 | **Windows 无法在本地适配器上存储蓝牙身份验证代码（链接密钥）** |

注册表侧：`BTHPORT\Parameters\Devices\D4B8FF93F635` 键现已不存在，绑定记录已丢失；与设备管理器报错 `0xC0000719`、"设备设置未从以前 OS 安装迁移"相互印证。

**断开原因推断（按可能性排序，尚未逐一证实）**：

1. **单主机绑定 / 原配优先**：BLE HID 遥控器通常只与一个已绑定主机工作。若它仍绑定原配 TV/盒子，或原配设备在附近抢占连接，新主机绑定不匹配时固件主动断开。
2. **bonding 未完成 / 加密认证失败**：两端均 `NOT BONDED`；遥控器可能要求加密绑定，GATT 枚举后未及时完成配对即被超时断开。
3. **本机蓝牙栈存不住链路密钥**：事件 18 表明 Windows 侧配对成功但密钥落库失败，重连认证失败导致断开；这是本机侧独立问题，需排查蓝牙驱动。
4. 低电、连接参数 / MTU 协商失败等次要因素。

**对可行性结论的影响**：连接不稳不改变"无 ATVV、语音走私有协议"的定性（服务树已在断开前枚举到）；但它会阻断后续读型号串、抓语音帧，需先按第五节步骤 5 稳住连接。

## 四、逐项可行性分析

### 4.1 扫描与识别

【代码】扫描白名单包含无后缀的"小米蓝牙语音遥控器"，所以本机**能出现在 SayAll 的扫描列表里**；但型号会被标成 `Unknown`，界面显示未知型号，不会被当作 RC001/RC003。

### 4.2 语音：核心卡点在协议，不在白名单

【代码】连接流程：设备名 → 找 ATVV 服务（`AB5E0001`）→ 找 0002/0003/0004 三个特征 → 订阅 audio/control → 能力协商 → 开麦推流。任一服务/特征缺失即报错（`VoiceServiceMissing` / `VoiceCharacteristicMissing`）。

【实测】本机 GATT 列表无 `AB5E0001`，双向私有通道是 `D1FF/A001` 与 `6287/6487`。因此：

- 直接连：大概率在服务发现阶段失败，语音会话建立不起来；
- 即使把本机名字 / 2A24 加进白名单伪装成 RC003，代码仍会去找 `AB5E0001`，找不到照样失败；
- 要打通语音，必须先逆向 `A001` / `6487` 这两条私有通道：语音键按下时的握手序列、上行帧头与分包、音频编码（是否仍是 IMA ADPCM、采样率、nibble 序、同步字 / predictor 下发方式）、续约与关麦时序。

【推断】老款 Realtek 透传方案的音频编码很可能与 ATVV 不同（可能是另一档 ADPCM / PCM / 私有压缩），解码器不能直接复用 `sayall-core` 现有 `ImaAdpcmDecoder`，需要按抓包结果重写或加分支。

### 4.3 按键：HID 键盘部分可复用，特殊键存疑

【实测】本机 `0x1812` HID 服务特征枚举为空（AccessDenied），与 RC003 取证一致；Windows 已把它挂成"符合蓝牙低能耗 GATT 的 HID 设备"（当前该节点状态 Error，未连接）。

- 方向键、确定、主页、菜单等走标准 HID 键盘页的键：在 Windows 上应能被 Raw Input 看到，官方基础按键映射（Raw Input + SendInput）路径可复用；
- 返回、音量±：RC003 上这三个键在 Raw Input 全通道零事件，靠提权 Helper 注入报告层才拿到；老款这几个键走哪条通道、是否同样不可见，**没有取证数据，不能承诺**；
- 语音键：本机语音键的按下/释放事件是否也走 HID，还是只走私有 Notify，需抓包确认。

### 4.4 可复用 / 需新写的代码边界

| 仓库模块 | 对本项目的可复用性 |
| --- | --- |
| `sayall-core`：PCM 处理、增益、帧累积、会话统计、配置 | 可复用（音频后处理与输出段与上行协议无关） |
| `sayall-windows`：WinRT BLE 枚举 / 连接 / 重连自愈、WASAPI 入队、VB-CABLE 端点识别、Raw Input、SendInput、UIA 聚焦 | 可复用框架；GATT 服务/特征 UUID 与协议解析需替换 |
| `sayall-core`：ATVV 能力解析、命令编解码、ADPCM 解码器、DecoderSync | **不可直接复用**，需按私有协议新写 |
| RC003 提权 Helper / Frida Gadget 报告层注入 | 仅在老款特殊键同样收不到时才需要评估，且要重新做设备归属取证 |

## 五、建议的验证步骤（由轻到重）

1. **连接态全量 GATT 复核（部分完成）**
   - ~~是否真的没有 `AB5E0001` 服务~~ **已完成：连接态服务树确认无 ATVV**（3.2）。
   - 待补：在 nRF Connect 点读 2A24 型号串、2A29 厂商串取值；
   - 待补：订阅 `A001`、`6487` 及各 2A4D Report 的 Notify，按住语音键说话，记录哪条特征出帧、帧长与字节形态。
2. **官方包实测对照**
   从官方 Releases 安装 SayAll，看扫描列表能否列出本机、连接时报错文案（预期卡在语音服务缺失）。这一步同时验证"改白名单是否够用"——预期不够。
3. **抓包定协议（仅当决定自研）**
   抓 HCI / GATT 流量，定位语音上行特征，解析帧头、编码与握手；对照 TV / 盒子端原配主机的交互序列。
4. **成本权衡**
   若目标只是 PC 无线麦，优先考虑直接入手 RC001 / RC003（官方已真机验收，开箱即用）；自研逆向老款的工作量、稳定性风险和售后成本明显更高。
5. **先解决"连接即断"（抓包前置条件）**
   - 换新电池排除低电；让原配 TV / 盒子关机或远离，避免单主机抢占。
   - 遥控器进入可配对模式（参考说明书，通常长按主页 / 返回组合键至指示灯快闪）；Windows 蓝牙设置里先删除旧设备，重启蓝牙适配器后重新配对。
   - 留意 nRF Connect 断开瞬间的 reason code（如 `0x13` 远端终止、`0x19` 不支持特性、`0x3D` 加密失败），据此区分是固件踢断还是认证失败。
   - 若 Windows 侧复现事件 18（链接密钥存不住），属本机蓝牙驱动 / 栈问题：更新蓝牙驱动或换外接蓝牙适配器再试。
   - 连接窗口很短时，趁断开前反复重连，优先读 2A24/2A29、订阅 Notify 抓语音帧。

### 本机环境现状（实测）

- 未安装 SayAll；未安装 VB-CABLE 虚拟声卡（音频设备仅 High Definition Audio）。
- 本机无 Rust 工具链（`cargo` 缺失）；有 `node`、`dotnet`。

## 六、主要风险与不确定性

1. **协议未公开**：Realtek 私有透传帧格式、音频编码无文档，逆向工作量不可预估；写私有特征有触发固件异常 / 重置配对的风险，探针阶段应只读不写。
2. ~~**枚举未在连接态复核**~~ **已闭环**：手机 nRF Connect 连接态全量服务树已确认无 ATVV（见 3.2）。
3. **型号代号未确认**：2A24/2A29 仍未读值，老款具体型号（XMRM-?）待在 nRF Connect 点 Read 补证；不影响"非 RC001/RC003、无 ATVV"的定性。
4. **按键与语音上行通道未取证**：本机 HID 含十余条 2A4D Report，另有 `A001`、`6487` 两条私有 Notify；返回 / 音量± / 语音键分别走哪条、语音帧从哪条上行，都需订阅通知后按键抓包，不能照搬 RC003 的 Helper 结论。
5. **编码与音质**：即便打通私有通道，采样率、降噪、回声消除、长录音续约等都要按新固件重新调，官方在 RC001/RC003 上踩过的闲置首用、粘键、队列溢出等坑可能需要重踩一遍。
6. **连接稳定性**：本机与手机均出现连上即断、两端未绑定；本机日志显示链路密钥配对后又被删除，且曾报告"无法存储链接密钥"。在绑定/单主机抢占问题解决前，难以稳定订阅 Notify 抓语音帧。

## 七、对 `gemini.txt` 方案的逐条核对

`gemini.txt` 的总体判断是"完全可行，只需改设备白名单 + 放开 8 kHz 采样率"。该结论建立在"本机与 RC001/RC003 底层协议一脉相承、只是老款 8 kHz"的假设上；此假设与本机实测和仓库代码均不符。下面分"成立 / 部分成立 / 不成立"三类核对。

### 7.1 Gemini 说法成立或基本成立的部分

| # | Gemini 说法 | 代码 / 实测依据 | 判定 |
| --- | --- | --- | --- |
| 1 | 虚拟声卡链路：装 VB-Cable，程序写 CABLE Input，输入法从 CABLE Output 拾音；WASAPI/cpal + 环形缓冲 + SendInput 联动输入法快捷键 | 与 SayAll 实际架构一致（`audio.rs` WASAPI 入队、虚拟声卡端点识别、按键 SendInput） | 成立 |
| 2 | 第一步零代码验证：配对后用 nRF Connect / BLE Explorer 看是否存在 `AB5E0001-…B664` | 验证思路正确；本机实测枚举**未见**该 UUID | 思路成立，本机结果与其乐观预期相反 |
| 3 | 代码对 8 kHz 有限制，需放开校验并做重采样 | 代码确实只放行 16 kHz：`atvv.rs` 123-128 选 codec 0x02→16k 否则 0x01→8k；`pipeline.rs` 82-83、107-108 对非 16k 报 `UnsupportedSampleRate`，测试 384 行断言 8000 报错；输出端 `audio.rs` 固定 16000 | 方向成立。措辞需修正：不是"遇到 8k 自动断开重连"，而是直接报错拒绝；即便放行解码器，输出端仍需补重采样到 16k/48k |
| 4 | ARN9 属于同源型号 | `lib.rs` 1633 型号匹配确含 `ARN9`；但本机广播名无后缀、2A24 未读出，**不能归入 ARN9** | 仅代码层面成立，套不到本机 |
| 5 | 报错里 `USB\VID_0483&PID_5710` 是历史遗留的 ST 外设 | `0x0483` 为 STMicroelectronics，属历史实例残留 | 成立 |

### 7.2 Gemini 说法与实测 / 代码冲突或属想当然的部分

| # | Gemini 说法 | 反证（实测 / 代码） | 判定 |
| --- | --- | --- | --- |
| 1 | "完全可行，二次开发工作量很小，只需改识别过滤 + 采样率配置" | 前提"底层协议一致"未被证实；实测本机无 ATVV 服务，语音候选是三条 Realtek 私有透传服务（`D1FF/A001`、`6287/6487`、`D0FF` 一族）。协议级通道、握手、编码都需新写 | **不成立** |
| 2 | "截图已 100% 确定支持 BLE GATT HID，可直接二次开发"；VID 0x2717 / PID 0x32B8 即锁定小米 MTK 方案同源 | `0x1812` 只是 HID over GATT 服务声明；VID/PID 是厂商与产品标识，不代表语音协议与 RC001/RC003 同源。本机 REV `4981`，服务集与 RC003 取证（REV `00A4`，含 ATVV + `8A7A0001` + `01BF` + `FE59`）明显不同；同 PID 不同固件/协议代际 | **过度推断** |
| 3 | "把 VID 0x2717、PID 0x32B8 加入支持列表"；代码按广播名 + VID/PID 锁定设备 | 仓库扫描**不读 VID/PID**：`lib.rs` 1669 仅按 `device.Name` 白名单过滤，型号由名称或连接后 2A24 决定。代码里没有 VID/PID 门禁可加；且名称白名单只决定能否进扫描列表，语音硬门禁是 ATVV 服务发现，加名字补不出服务 | **与代码不符** |
| 4 | "情况 B：语音包封装在 HID Report，用 hidapi 监听 Report ID，字节流直接喂现有 IMA ADPCM 解码器即可出人声" | 本机实测语音候选通道是 GATT Notify 私有特征，不是 HID Report；编码是否 IMA ADPCM、采样率、帧头/同步字均未抓包确认，现有解码器不能假定可直接吃私有字节流 | **无证据的乐观假设** |
| 5 | 0xC0000719 / "未从以前 OS 安装迁移" 印证"走私有 GATT 语音协议（如 ATVV）"；HID 驱动拒载反而让用户态 hidapi 无阻拦直连 | 该报错只能说明 HID 类驱动绑定/报告描述符校验失败，推不出语音协议类型。上层 HID 驱动拒载不影响 WinRT GATT 枚举（实测确实能枚举到服务）这点基本对；但本机语音不在 HID Report 通道，hidapi 路线不适用 | **因果跳跃，部分正确** |
| 6 | 语音键通常发 Consumer Page 0x0C 下 0x0221 搜索键 / 0x00CF 语音指令键 | 本机语音键走 HID 还是私有 Notify 未取证，键值码未抓包；该值是通用经验值，不能直接绑定 | **待取证，不可直接采用** |
| 7 | 复用现有 ADPCM 解码器、四模块改造即可 | `sayall-core` 的能力解析、命令编解码、DecoderSync、会话状态机与 ATVV 语义强耦合；私有通道的握手时序（开麦/续约/关麦）、分包同步、编码器选型都要新写，不可整体复用 | **低估改造范围** |

### 7.3 仍需独立核实的引用

- Gemini 称"同源开源项目 open-voice-bridge 已验证早期普通款（ARN9）可复用同一套框架"：本仓库内未见对该项目的引用，本次调研也未独立核实；ARN9 虽在本仓库型号匹配列表内，但不能据此认定本机为 ARN9。

### 7.4 核对后的结论

Gemini 方案中**音频后处理与虚拟声卡路由部分可参考**，但其核心前提（本机与 RC001/RC003 协议同源、仅老款 8 kHz）被本机 GATT 实测否定。正确的第一步仍是连接态用 nRF Connect 复核：有无 `AB5E0001`、2A24 型号串、按住语音键时哪条 Notify 出帧。若确认无 ATVV，则要么更换 RC001/RC003，要么按私有透传通道做协议级逆向（见第五节步骤 3 与第四节 4.2）。
